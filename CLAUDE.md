# Cargo CRM — правила работы в репозитории

Это MVP внутренней системы: CRM + казначейство (заявки на оплату) + склад (WMS).
Цель — демонстрируемый продукт для подачи ТОО в Astana Hub. Срок 3 недели, объём зафиксирован в `docs/backlog.md`.

## Читать перед любой задачей
1. `docs/architecture.md` — стек, модули, инварианты, соглашения по коду и БД.
2. `docs/ux.md` — правила интерфейса. Это главное требование заказчика сверх ТЗ.
3. `docs/backlog.md` — своя задача: состав работ, критерии приёмки, зависимости.
4. `docs/acceptance.md` — сценарии приёмки, которыми проверяется результат.

## Как ведём работу
- Одна задача бэклога = одна ветка `task/DEV-0NN-короткое-имя` в своём git worktree. В `main` сливает только ведущий после ревью.
- Задача считается сделанной, когда: критерии приёмки выполнены; `make check` зелёный; статус задачи в `docs/backlog.md` обновлён; в `docs/devlog.md` добавлена строка.
- Не выходить за рамки задачи. Увидел проблему рядом — запиши в `docs/devlog.md` в раздел «Замечено», не чини молча.
- Новая зависимость (Go-модуль или npm-пакет) — только если без неё задача заметно сложнее, и с одной строкой «зачем» в `docs/architecture.md`.
- Ничего не придумывать сверх ТЗ: интеграции с 1С, банками, ЭСФ — не делаем и не заявляем как готовые.

## Код
- Язык кода и идентификаторов — английский. Комментарии, сообщения коммитов, тексты интерфейса, документация — русский.
- Комментарии пишем только там, где неочевидно «почему». Не пересказывать код.
- Никаких упоминаний ИИ-ассистентов в коде, коммитах, PR и документации. Без строк `Co-Authored-By`.
- Сообщение коммита: первая строка `DEV-0NN: что сделано` (до 72 символов), при необходимости тело по делу.
- Бэкенд: Go, стандартная библиотека в приоритете. Ошибки оборачивать с контекстом (`fmt.Errorf("...: %w", err)`). Бизнес-правила — в сервисах модуля, не в хендлерах и не в SQL-запросах sqlc.
- SQL: миграции goose в `backend/db/migrations`, запросы sqlc в `backend/db/queries/<module>`. После правки запросов — `make sqlc`, сгенерированный код коммитим.
- Фронтенд: TypeScript strict, компоненты shadcn/ui из `src/components/ui`, типы API — только сгенерированные из OpenAPI (`make api-types`), руками типы ответов не писать.
- Все тексты интерфейса — через `t('ключ')` из `src/i18n/ru.ts`. Это задел под казахский; переводов сейчас не делаем.

## Документация
- `README.md` — только что это и как запустить. Не раздувать.
- Архитектура и решения — `docs/architecture.md`. Лог разработки — `docs/devlog.md`. Деплой — `docs/deploy.md`.
- Схема БД описывается миграциями; обзор таблиц по модулям держим в `docs/architecture.md` актуальным.

## Проверка
- `make check` — vet, тесты бэкенда, typecheck и сборка фронтенда. Запускать перед тем, как объявить задачу готовой.
- Для тестов бэкенда нужен Postgres: `make dev-db` поднимает его в Docker, `TEST_DATABASE_URL` см. в `Makefile`.
- Проверка «вживую» через браузер обязательна для задач с интерфейсом: открыть экран, пройти сценарий, посмотреть на телефонной ширине.
